# 数据存储

PostgreSQL 保存账号与业务关系，Git 保存网站可编辑内容及版本历史。

| 数据 | 存储位置 |
| --- | --- |
| 用户、密码摘要、会话摘要与过期时间 | PostgreSQL |
| 网站与草稿的用户所有权 | PostgreSQL 关联表 |
| 已发布网站标识、远端地址与发布 commit | PostgreSQL `sites` |
| sandbox 标识、同步状态与版本信息 | PostgreSQL `site_drafts` |
| 网站配置、页面源码、构建程序、资源与公开文件 | sandbox Git 仓库及远端版本仓库 |
| 页面列表索引 | PostgreSQL `pages`，按 `draft_id` 与 `page_id` 共同标识 |
| 知识库、生成任务、询盘、报告与集成配置 | PostgreSQL |
| 远端公开网站文件 | 与已发布 commit 对应的独立发布目录 |

同一页面在不同草稿中保留相同 `pageId`，每份草稿分别保存页面索引。完成 Pull 后，管理 API 根据合并后的源码更新索引，包括页面删除。

源码中的内容是页面编辑与构建的依据。数据库索引用于查询和权限管理，不能代替 Git 中的已发布版本。已发布页面查询必须对应网站的 `publishedCommitId`。

同步操作保存待执行动作、远端标识和错误信息。进程重新启动后，系统根据持久化状态继续处理，并检查远端已经发布的版本。失败操作不得重复创建网站。

多个用户移除所有者时，数据库事务必须保证至少保留一名所有者。同一草稿的编辑、同步和发布操作需要互斥，操作开始时检查当前权限。

迁移已有数据时，网站内容与配置进入对应草稿的 Git 仓库，所有者由显式的账号映射确定。尚未在独立远端发布的内容保留为草稿。询盘、邮件任务、报告、事件和集成配置保留原记录标识及关联，通过 `draft_id` 归属未发布草稿；首次发布后关联实际网站。用户可以在草稿中访问历史记录。

迁移在修改表结构前检查完整的所有权映射、账号和数据引用。数据库变更在同一事务内完成，并验证 sandbox 中的源码和 Git 版本。失败时保留原有数据库，重试使用稳定的迁移标识。迁移测试覆盖所有业务表的字段、主键、关联与重复执行。
